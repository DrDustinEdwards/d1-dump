## Threat model (STRIDE)

The package copies a site's D1 database into that site's own R2 bucket, prunes old runs, reports the age of the newest complete run, and can rebuild a run into an empty database. The thing it can lose is a run marked complete that does not hold the rows, a prune that deletes the only copy, or a workflow token that can push.

Who can call it: the site's scheduled Worker, which holds the D1 and R2 bindings; a person who runs `d1-dump drill` against a downloaded run; a person who passes a Cloudflare API token to the d1 backend; and GitHub Actions on pull request, push to `main`, a `v*` tag, a Monday cron, and `workflow_dispatch`.

Entry points:

- Library: `dumpDatabase`, `runCheckedBackup`, `writeCompleteMarker`, `pruneDumps`, `backupHealth`, `latestDump`, `restoreDump`, `runRestoreDrill`, `selectStaleRuns`, `readPlan`.
- CLI: `d1-dump drill`. sqlite needs no credential. d1 needs `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`.
- Workflows: `ci.yml` (pull request and push to `main`), `ai-author.yml` (same), `pr-footer.yml` (pull request), `code-map.yml` (push to `main`, cron `17 4 * * 1`, dispatch), `bump-consumers.yml` (tag `v*` and dispatch).
- No HTTP server, MCP tool, queue, or webhook. The site's own cron calls the library. This repo does not declare that cron.

Where trust changes:

- Table names and `CREATE` statements come from `sqlite_master`. Identifiers are quoted. On restore, those `CREATE` statements are executed in the database the caller passed.
- The R2 bucket is trusted. The marker is a JSON list of keys, row counts, and FTS modes. There is no digest of the bytes.
- `runCheckedBackup` writes the marker only after `standardProblems` and the site's `check` return no messages. A failure leaves the objects and prunes nothing.
- `pruneDumps` refuses to select anything while no run is complete. It deletes a stale run's marker before the rest of that run. A bucket lock (R2 error 10069) skips that run and continues.
- The d1 scratch backend creates and deletes only a name that starts with `restore-drill-`. The token is the caller's env. The README says that token can create and delete every D1 database on the account, and to keep it out of scheduled CI.
- Caller commands in the pinned devkit code-map job run as shell in a job whose token can push (DD-2).

Spoofing: the drill's sqlite backend needs no credential. The d1 backend sends the token only as `Authorization`. Errors include the status and Cloudflare's message, and a test locks that the token is not in the message.
Tampering: `main` is unprotected (DD-2). A dump is one D1 batch for every table that is not paged, so those tables are one transaction. A paged table is read again after that batch, and a short page can still be marked complete (DD-1).
Repudiation: a failed night keeps its objects and withholds the marker, so the health age keeps growing. There is no separate audit log.
Information disclosure: the default dump includes every dumpable table. Excluding a credential table is the caller's `exclude` list. A name that is not a table fails the run. `backupHealth` puts at most 80 characters of an error into `warning`.
Denial of service: one table file is held as a string and as parsed rows. The README budgets about 40 MB for a table file inside a Worker. Prune lists the prefix and deletes in chunks of 1000 keys.
Elevation: the REST adapter refuses a scratch name that does not start with `restore-drill-` before any request. `directoryBucket` is read-only and refuses a key whose resolved path leaves the directory.

## Findings

### DD-1 MAJOR, correctness, confirmed by running

Files: `src/dump.ts` lines 73-84 and 130-135, `src/backup.ts` lines 33-49.

A paged table is not part of the snapshot batch. The batch reads `MAX(id)`. The pages then run `SELECT * ... WHERE id > ? AND id <= ? ORDER BY id LIMIT ?`. The marker records how many rows those pages returned. Nothing compares that number to a count taken in the snapshot.

`pageRows: 0` is a legal option. SQLite treats `LIMIT 0` as no rows. Probe, real `node:sqlite`, table `audit` with three rows, table `posts` with one:

```json
{"exported_at":"2026-10-21T00:00:00.000Z","table":"audit","rows":[]}
```

`runCheckedBackup` with `required: ["audit", "posts"]` and `paged: { audit: { idColumn: "id", pageRows: 0 } }` returned `complete: true` and wrote `_complete.json`. `standardProblems` only fails when every table is empty or a required name is absent. `audit` is present with 0 rows, and `posts` supplies the one row that lets the total pass.

The same hole is any paged read that returns fewer rows than the snapshot held: a non-unique id (the next page uses `id >` the last id of this page, so further rows with that id are skipped), or rows deleted after the `MAX` was read. The README limits paging to an append-only integer id. The code does not check that the stream matched the snapshot.

Path: a nightly `runCheckedBackup` pages the large table with `pageRows: 0`, or with a page size that skips rows. The marker is written. `backupHealth` reports a fresh dump. `restoreDump` rebuilds the empty file and the counts match the marker, so the drill's count check passes. The rows are gone, and the age warning does not fire.

Smallest fix: reject a `pageRows` that is not an integer greater than or equal to 1. In the snapshot batch, also read `COUNT(*)` for `id <= max_id`, and refuse the marker when the streamed count differs.

Checked and clean, apart from DD-1 and DD-2:

- Identifiers. `quoteIdent` doubles embedded quotes. Table names in `SELECT`, `INSERT`, `PRAGMA table_info`, and `COUNT(*)` go through it. The snapshot SQL is a fixed shape plus a quoted name.
- Virtual tables. Anything that is not FTS5 throws before a dump is written (`src/schema.ts` lines 96-101). Shadow tables are left out. The names `_cf_` and `sqlite_` are left out.
- Restore SQL. `CREATE` statements from `_schema.json` are prepared and run in the caller's destination database. Inserts are `INSERT ... VALUES (?1, ?2, ...)` with the values bound. A row's size is not in the SQL text. The drill wraps the destination in `guardStatements`, which throws before a statement over 100,000 UTF-8 bytes is sent. Disabling that throw made `test/drill.test.ts` stay green on the cap, which is the failure the test locks. Direct `restoreDump` does not use the guard. Its own inserts are short. A `CREATE` over the cap would be sent and D1 would refuse it.
- REST. A bound array is refused with a message that says a BLOB cannot be drilled over REST. The token is not copied into the error. A test posts a failing response whose body says "bad token" and asserts the thrown message has no token.
- Scratch names. Both backends throw before creating anything whose name does not start with `restore-drill-`.
- Directory reads. `directoryBucket` refuses `../outside.json` and `..\outside.json`. On this Windows machine, a key `C:/Windows/win.ini` resolved underneath the dump directory and returned null. It did not open `C:\Windows\win.ini`.
- CSRF, sessions, OAuth, JWT: none. There is no HTTP listener.
- Headers. This package sets `content-type: application/json` on the objects it writes. It serves no response.
- Health text. `backupHealth` never throws. A read error becomes a warning of at most 80 characters.

`exclude` is the only control that keeps a credential table out of R2. The first README sample calls `dumpDatabase` with no exclude. The `runCheckedBackup` sample excludes `session` and says a backup must never carry credential tables. A name on that list that is not a real table fails the run, so a renamed table does not silently stay in the dump. The caller still has to name it.

### 4. Data integrity

Checked and clean, apart from DD-1 and DD-5:

- The marker is written last. A planted failure on the second `put` leaves objects and no marker, and `restoreDump` refuses the prefix. `runCheckedBackup` writes the marker only after the checks, then prunes. A failing night leaves the previous complete run. Disabling the `problems.length` throw made the missing-required test receive a successful result. The test went red.
- `selectStaleRuns` returns nothing when no run is complete. That is the emptied-bucket case. Disabling the early return made the test throw on `complete[0]`. The test went red. The newest complete run is in the keep set even when it is older than every window. A 200-day history and a year boundary are locked to an explicit list of dates.
- Incomplete runs hold no daily, weekly, or monthly slot. They stay while their day is inside the daily window, then age out. A flat `retentionDays` / `minKept` policy keeps the newest complete runs and does not give an incomplete run a floor slot.
- Delete order. The marker goes in its own call, then the other keys. A lock that refuses only the table file removes the marker, counts the run in `locked`, and leaves the table object. `latestDump` then skips it. A lock that refuses the marker deletes nothing of that run. A later prune of an unlocked bucket deletes it. An error whose message is not a lock still throws. Disabling the lock catch made the 10069 test throw. The test went red.
- `kept + pruned + locked` equals the number of runs under the prefix. The half-refused run is counted in `locked`, not in `kept`.
- A second complete run on the same UTC day is stale at once. The test keeps `2026-09-20T09` and drops `2026-09-20T02`.
- Restore refuses a table file whose array length differs from the marker, a column missing from every row, an extra column, and a `COUNT(*)` after insert that differs from the marker. Disabling the array-length check still threw `comments restored 2 rows, the dump holds 3`. The recount is a second guard. The test is pinned to the first message, so it went red.
- Row counts are the integrity check. The marker does not store a digest of the table file. A file with the same columns and the same number of different rows would restore. That is the residual. DD-1 is the case where the count itself is the empty stream.
- The copy lives in the site's own R2 account. Time Travel is the in-account restore the README points at. Taking a copy outside the account is the caller's step. This package writes the site's bucket.

A young run whose marker is deleted and whose remaining objects are locked becomes an incomplete run inside the daily window. The next prune does not select it until that day leaves the window. That matches the incomplete-run rule. The README's sentence that a later prune retries a locked run once the lock ages off describes a run whose marker delete was refused, so the run is still complete and still stale.

### 5. Correctness

Checked and clean, apart from DD-1:

- FTS5. External content is rebuilt with `INSERT INTO <fts>(<fts>) VALUES ('rebuild')` after the rows. Internal content is dumped with `rowid` and inserted. Contentless is created empty. Shadow tables are not dumped. A dropped rebuild fails the drill's `fts` and `search` checks. The roundtrip compares posts, comments, glossary, settings, the view, both searches, the trigger on a new row, and the next AUTOINCREMENT id.
- Parents. `REFERENCES` is read from the `CREATE` text. The parent is ordered first. Each insert batch starts with `PRAGMA defer_foreign_keys = ON`. Triggers, indexes, and views are created after the rows, so a trigger does not fire twice.
- BLOBs. D1's array of bytes round-trips. The sqlite backend returns `typeof(cover) = blob` and `hex` `00FF10`. The REST backend refuses the array.
- A 141 KB value with quotes, newlines, and carriage returns restores byte for byte on both backends. The longest statement in that drill stays under 100,000 bytes. The same characters as a SQL literal are refused by the test's D1 with `statement too long` or `SQLITE_TOOBIG`.
- `wrangler d1 export` on a database with FTS5 exits 1, writes no file, and the message matches `cannot export databases with Virtual Tables (fts5)`. The same database without FTS5 exports. `dumpDatabase` dumps the FTS5 database. Those three tests passed.
- `backupHealth` skips a newer incomplete run, warns past 26 hours, warns when there is no complete run, and warns instead of throwing when `list` throws.
- Sidecar names are `[a-z0-9-]+`. `complete` and `schema` are reserved. A sidecar that would overwrite a table name throws.
- `writeCompleteMarker` refuses a result that is already complete. The marker's `keys` list is the objects written before the marker.

Integers past 2^53 lose precision because the values pass through JSON and D1's JavaScript API. The README says so.

### 6. Reliability

Checked and clean:

- A scratch database is deleted in a `finally`. A delete that throws is a failed `scratch` check that names the database. The sqlite backend removes the temp directory and throws if it is still there.
- Multipart upload aborts on failure. If the abort also fails, the error is an `AggregateError` that keeps both causes. Those lines are among the uncovered ones in `src/r2.ts` (49-52).
- Batches cut at 100 rows or about 1 MB of bound text and BLOB. One row over 1 MB is its own batch. The 1.5 MB drill asserts `maxBatchBound` stays under two such rows.
- Prune continues after a lock and stops on any other delete error.
- Workflow timeouts: CI 20 minutes, code-map 20 on push and 120 when mutation runs. Code-map concurrency does not cancel an in-progress run.
- `backupHealth` cannot take down a health route by throwing.
- Two dumps that share one `now` value write the same run id. `runIdFor` is the ISO time with `:` and `.` replaced, so the resolution is one millisecond. An overlap of that form can interleave objects under one prefix. The marker is last, and a mixed file fails the row-count check unless the counts happen to match. The scheduled caller normally uses `new Date()` once per invocation.

No Workers CPU limit is configured here. The site that mounts the call owns the isolate. The README's 40 MB table-file budget is the limit this package documents.

### 7. Performance and cost

No database of this package's own, so there is no `EXPLAIN QUERY PLAN` to run. The SQL this package sends is against the caller's tables:

- One `sqlite_master` read.
- One batch of `SELECT *` or `SELECT MAX(id)`, one statement per dumped table. A primary key on the paged id makes the later `WHERE id > ? AND id <= ? ORDER BY id LIMIT ?` a range on that key. That plan was not measured.
- On restore, one `COUNT(*)` per table and one `PRAGMA table_info` per non-empty table.

The expensive cron is the Monday code-map mutation (five Stryker chunks, 120 minutes), not a backup. The backup cost is the site's scheduled invocation: one read of every table and one R2 object per table, plus a prune that lists the prefix.

A paged upload uses 8 MiB parts. R2's minimum part size, except the last, is 5 MiB. A single short object is one part. The 9.6 MB test crosses one part boundary and restores the byte total.

API responses: this package serves none. Objects are written as `application/json`.

### 10. Architecture and simplicity

The real structure: a Worker calls `runCheckedBackup` with its D1 and R2 bindings. The library reads `sqlite_master`, writes one JSON object per table, writes the marker, and prunes. Health reads the newest marker. Restore reads the marker and the schema sidecar into an empty database. The drill does that into a scratch database and deletes it. From Node, the scratch is a local SQLite file or a D1 database over REST, and the dump can be a directory. Workflows call devkit. There is no second storage client and no HTTP framework.

The README describes that shape, including the FTS5 cases, the lock behavior, the statement cap, and what the sqlite backend cannot prove about remote D1. The code matches those sections on the paths that were run.

Over-engineering: graduated retention is more mechanism than a flat 90 days. `selectStaleRuns` is pure and the tests name every kept day. I would not delete it. The flat policy remains for a caller that passes `retentionDays` or `minKept`.

Under-engineering: the paged path trusts the caller to pass a positive page size and an append-only id (DD-1). A digest is the other missing check, and it is named above as a change, not a second finding.

Shared code: this package is the shared copy. Callers should not keep a local dump. Nothing here should move into site-runtime or site-api.
